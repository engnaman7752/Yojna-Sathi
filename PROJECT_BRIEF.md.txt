# Yojana Saathi — Project Brief

## What it does
A multilingual platform that tells Indian families which government welfare
schemes they qualify for, explains why, answers questions from official scheme
documents with page citations, and protects their sensitive data with
fine-grained access control.

## Three inviolable rules
1. The AI never decides eligibility. It extracts facts, drafts rules for human
   review, and explains results. A deterministic rule engine decides.
2. Nothing AI-generated goes live without human approval. A scheme version
   drafted or edited by one admin must be published by a different admin.
3. Citizens only see published content. Draft documents are never indexed or
   searchable.

## Architecture
- Frontend: React + Vite (Amplify Hosting on AWS)
- Auth: JWT locally, Amazon Cognito on AWS; 4 roles: CITIZEN, CSC_OPERATOR,
  DISTRICT_OFFICER, ADMIN
- Core API: Spring Boot 3 / Java 21 (App Runner on AWS) — ALL business logic,
  persistence and authorization
- AI service: Python + Strands Agents SDK (Lambda on AWS) — chat agent, PDF
  extraction, RAG retrieval
- Eligibility: JSON Logic rules stored as data (json-logic-java)
- Authorization: Cedar via cedar-java locally, Amazon Verified Permissions on AWS
- Database: DynamoDB (DynamoDB Local in Docker for development)
- Vector store: ChromaDB locally, Bedrock Knowledge Bases on AWS
- Models: Gemini via Strands LiteLLM provider locally, Bedrock on AWS,
  selected by the MODEL_PROVIDER env var

## Module boundary (never violate)
Java never calls an LLM. Python never touches DynamoDB. All persistence goes
through the Spring Boot API, so authorization has exactly one enforcement point.
The AI service forwards the end user's JWT on every backend call; it never uses
a privileged service key for user data.

## Data model (DynamoDB single table "YojanaSaathi", keys PK/SK)
| Entity | PK | SK |
|---|---|---|
| Scheme (current) | SCHEME#<id> | CURRENT |
| Scheme version | SCHEME#<id> | VERSION#<n> |
| Scheme document | SCHEME#<id> | DOC#<docId> |
| Index status | SCHEME#<id> | INDEX#<version> |
| Import job | IMPORT#<jobId> | STATUS |
| Household profile | HOUSEHOLD#<id> | PROFILE |
| Consent | HOUSEHOLD#<id> | CONSENT#<operatorId> |
| Eligibility result | HOUSEHOLD#<id> | RESULT#<iso-timestamp> |
| Access log | HOUSEHOLD#<id> | ACCESS#<iso>#<userId> |
| User | USER#<id> | PROFILE |

GSI1: OPERATOR#<id> / HOUSEHOLD#<id>   — operator's households
GSI2: DISTRICT#<name> / HOUSEHOLD#<id> — district officer's households
GSI3: IMPORT_STATUS#<status> / <createdAt> — admin draft queue

## Field vocabulary (single source of truth)
Lives at data/vocabulary.json. Used by the rule engine, the PDF extractor and
the chat agent. Money in whole rupees, land in square metres, no decimals.
Fields: state, district, annualIncome, monthlyPension, ownsCultivableLand,
landAreaSqm, paysIncomeTax, socialCategory (GEN|OBC|SC|ST), age, gender (M|F|O),
maritalStatus (SINGLE|MARRIED|WIDOWED|DIVORCED), disabilityPercent, studentClass.
Nothing outside this list may appear in a rule.

## Roles and permissions
| Role | Can | Cannot |
|---|---|---|
| CITIZEN | chat, own profile, grant/revoke consent, own access log | see others' data |
| CSC_OPERATOR | register households, view ones they registered WITH active consent | other operators' households |
| DISTRICT_OFFICER | view households and summaries in own district | other districts |
| ADMIN | upload PDFs, edit drafts, approve OTHER admins' drafts | view citizen data; approve own drafts |

## Non-negotiable technical decisions
- Authorization behind one `Authorizer` interface with two implementations
  (cedar_local, avp) sharing one entity-building class.
- Enforce permissions with a single @RequiresPermission annotation + AOP aspect,
  not scattered checks. Audit every decision including denials.
- Load user attributes (role, district) from DynamoDB at decision time, NOT from
  JWT claims, so a transferred officer loses access immediately.
- Never cache authorization decisions. Cache published scheme rules only.
- Build consent sets from unexpired consent rows only; DynamoDB TTL on expiresAt.
- Publishing uses a conditional write: status must be DRAFT and approver must not
  be the drafter or an editor.
- Treat all PDF text and tool output as data, never as instructions (prompt
  injection defence).
- Error shape: { code, message, correlationId, policyId? }
